# 3. Read the permissions

*Public means you could see it. It does not specify what you may do with it.*

A public repository includes a function that appears ideal for Shelf Kite. Someone copied it into the demo build. The host let the team browse the source. The team still needs to determine whether the relevant rights holder permits copying and distributing that function under the proposed terms. A link in the credits cannot create a license.

## Make the permission test narrow

Start with the asset and the exact version. Look for a root license, a file-level notice, dependency metadata, exceptions for third-party materials, or a separate written permission. Ask which parts are covered and whether the grantor can authorize them. A license on an example repository need not cover a separate font, screenshot or logo checked into it.

Then write the intended action. You might need to copy the code, change it, ship a binary or distribute source. Mark conditions tied to each action: retention of notices, accompanying license text, or source-provision requirements where applicable. Check whether the team can actually satisfy the conditions. Do not assume all public repositories have identical terms or that the current main branch terms cover an older version.

| Evidence | Supported classroom action | What remains unresolved |
| --- | --- | --- |
| Public URL and no permission located | Record the source and hold the copy out of the proposed public release | Whether a grant, applicable exception or replacement resolves it |
| Written permission to display an image on one course site | Preserve that record and scope any display to the stated use | A downloadable asset or external promotional reuse |
| Exact version with a terms file; individual image excluded | Read and satisfy conditions for covered parts | A separate basis for the excluded image |

The first row is not a claim that every unlicensed-looking use is unlawful. U.S. copyright has limits and exceptions. [17 U.S.C. §§ 106–107](https://www.copyright.gov/title17/92chap1.html#106) describe exclusive rights and the case-specific fair-use inquiry. Its factors include purpose and character, nature of the work, amount and substantiality, and market effect. “Educational” or “small” alone does not decide the outcome. Refer uncertain exceptions rather than approving them in a register.

## Replace an artifact, not just its filename

If the team removes a problematic function from the latest tree but publishes an archive with the old commit or bundles an older build, the release still needs attention. Check the actual package, version and deliverable, not only the green box in a spreadsheet. A clean version that points to different evidence deserves a separate row.

Optional tool route: Give a model an invented excerpt and a proposed use. Ask it to list missing evidence and quote the exact clause it relied on. Compare those clauses to the source yourself. Do not give it confidential contracts, unpublished code or student data. The no-tool route uses the same excerpt and writes that check by hand. An answer that cannot point back to a clause is not evidence of authority.

**Try it unaided.** Written permission covers display during a live class meeting. Is distribution in a public repository documented by that text? Rewrite the record to distinguish what is supported from the decision you would refer.
